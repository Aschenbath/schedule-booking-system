# 设计文档（一页）

## 1. 总体结构

```
浏览器 (Vue SPA) ──REST/SSE──> Hono 服务 ──> SQLite (node:sqlite)
                                  │
                                  ├─ Agent（两段式对话）
                                  │    ├─ 抽取：LLM(openai 兼容) 或 规则(rules)      ← “听懂”
                                  │    ├─ 业务：时间解析 / 名单展开 / 冲突 / 车程 / 缺项 / 幂等  ← 代码
                                  │    └─ 回复：LLM 流式 或 模板                       ← “措辞”
                                  ├─ 地图服务：mock | amap | failing（统一 MapService 接口 + geocache）
                                  ├─ 通知 Hub：每条通知只投递给同一用户的一个 SSE 连接
                                  └─ 提醒调度：每 5s 扫描，(用户,类型,事件) 唯一
```

一次对话回合固定为三步：**抽取增量 → 代码合并与判断 → 生成回复**。模型两次出场都不碰数据库，也不做任何“该不该”的判断。

## 2. 工具划分：哪些交给代码，哪些交给模型

| 环节 | 归属 | 原因 |
| --- | --- | --- |
| 类别、主题、地点、来访方、人数、备注的抽取 | 模型（规则模式兜底） | 自然语言理解是模型的长项；输出限定为 JSON 增量，便于校验 |
| 时间表达 → 具体时刻 | **代码**（`time/parse.ts`，模型只摘录 `time_text` 原话） | 依赖 NOW 与时区，模型算日期常错；代码可测、可复现 |
| 改口合并（“算了改成后天”只换日期，“改到5点”继承下午） | 代码 `mergeTime` | 保留已收集信息是硬约束，不能靠模型记忆 |
| 部门 / 岗位标签 → 具体人 | 代码 `people.ts` 查通讯录 | 名单必须来自数据库；空部门要如实报“没找到人” |
| 缺哪些字段、一轮最多问两个 | 代码 `missingFields` + 类别必填表 | 追问节奏是产品规则，不交给模型即兴 |
| 时间冲突、车程是否赶得上、空档推荐 | 代码 `schedule.ts` + MapService | 需要精确区间运算与外部接口；失败要标 `unverified` 而不是猜 |
| 提交、审批、写日程、通知、提醒 | 代码 + 数据库唯一约束 | 幂等和事务只能在代码层保证 |
| 意图（提交 / 取消 / 重来 / 确认名单） | 模型抽取，代码执行 | 模型识别口语，代码决定后果 |
| 面向员工的措辞 | 模型（模板兜底） | 让对话自然；但只能复述代码算出的“事实”，不允许新增事实 |

模型任何一步失败（超时、非 JSON、接口报错）都自动回退到同一接口的规则实现，对话不中断；测试全部在规则模式下运行。

## 3. 提示词内容

**抽取提示词**（`llm/prompts.ts: extractSystemPrompt`）每回合动态生成，包含：

1. 角色边界：“只把这一句话里新提供或修改的信息抽成 JSON，业务判断由程序完成”；
2. 当前时间（含星期、时区），让模型能给出 `start/end` 的参考推断，但 `time_text` 原话才是代码解析的依据；
3. 输出 schema：`category / subject / time_text / start / end / location / visitor / counterpart / headcount / note / people_queries / remove_people / intent`，未提及一律 `null`；
4. 类别判定规则与“判不准输出 unsure，绝对不要猜”；意图规则；改口只输出变化字段；
5. 上一轮追问的字段列表（简短回答归到对应字段）；
6. 通讯录里可用的部门、岗位标签、姓名（限制模型只用真实存在的称呼，且不自行展开成名单）；
7. 当前草稿快照（避免重复输出未变化字段）。

**回复提示词**（`REPLY_SYSTEM_PROMPT`）固定不变，输入是程序算好的【事实】JSON，规则按事实字段逐条对应：`askCategory` → 问类别；`questions` → 最多两个问题；`people.expansions` → 逐个复述展开结果，空名单必须说“没找到成员”；`analysis.conflicts` → 指出重叠并列空档；`enough=false` → “时间上不冲突，但车程赶不上”+ 建议；`travel.status=unverified` → “地图接口调用失败，车程未核实”；`ready` → 总结并请提交；`submitted.duplicate` → 说明未重复创建。结尾是禁止清单：不编造时间/地点/人名，不说“已通知/已安排”，不输出 JSON 或 markdown 标题。

## 4. 几个关键决定

- **模型不做时间运算。** 规则解析器覆盖“明天/后天/下周二/这周五/上午/下午/X点半/X点到Y点/中文数字/时长”，已过的时刻顺延，改口只替换变化的部分。
- **名单必须过一次人眼。** 展开结果以卡片列在对话里，可勾选后“确认名单”；提交也视为确认。空展开不算“已有参会人”，会继续追问。
- **车程用规则判断、地图只提供数字。** `minutes(A→B) + 缓冲 > 间隔` 即为赶不上；地图失败结果不进缓存，标 `unverified`，一路带到审批卡片与日程页。
- **幂等靠数据库。** 请求幂等键（对话 + 内容哈希）唯一；`events.request_id` 唯一；审批用事务内 `UPDATE … WHERE status='pending'`，第二次审批不会再建事件、再发通知。
- **提交之后，对话与老板看到的必须一致。** 改造前：请求一提交，对话里再改时间/地点只改本地草稿，老板那边仍是旧请求，助手却可能说“已改好”；说“取消”也只清草稿，待批准里的请求还在。改造后：请求多了 `withdrawn` 状态，只有发起人能撤回、只能撤回 `pending` 的（事务内条件更新，与审批互斥）。提交后改了内容 → 原请求原样保留，回复明确“还没发给老板”，按钮变为“撤回原请求并重新提交”，点击后先撤回再新建；说“不约了” → 撤回并通知老板（`request_withdrawn`）；老板已同意 → 对话锁定，改或取消都只如实说明现状，请员工直接联系老板；被拒 → 说明原因，改好可再交。模型抽取要几秒，抽取完成后会重读请求状态，避免按过期状态行事。代价：多一个状态和一类通知，老板端历史与提醒中心都要识别“已撤回”；已同意的日程不能在对话里改，只能线下沟通。验证：`postsubmit.test.ts` P1–P8 离线通过，并在部署环境用真实模型跑通端到端冒烟。未覆盖：老板改期后发起人再协商的流程仍需线下完成。
- **通知单点投递。** Hub 对每条通知只写给该用户的一个连接并记 `delivered_at`，其余标签页只收到 `refresh`；页面关着时错过的提醒在下次连接时补投一次。

## 5. 怎样发现“静默的错误行为”（没报错，但做错了）

已经落地的手段：

1. **事实与措辞分离。** 界面上的名单卡、冲突/车程卡、预约摘要卡全部由代码事实渲染，不解析模型文字；模型说错了，卡片仍是对的，两者不一致一眼可见。
2. **数据库不变量。** 唯一索引兜住“一个请求两条事件”“一个事件两条提醒”“同一人重复通知”这类错误，违反即抛错而不是静默重复。
3. **离线场景测试断言的是结果，不是措辞。** 例如 S6 断言“回复不含‘已通知’且 draft 仍缺参会人”，S5 断言 `travelStatus === 'unverified'` 一路出现在审批视图，S11 断言事件数恰为 1。
4. **失败显式化。** 地图、模型失败都变成状态字段（`unverified`、`llm: rules` 回退标记在 `/api/meta`），而不是默认值。

可以进一步做（未实现）：

- 回复后置校验：用正则/小模型检查回复里出现的时间、人名、地点是否都在事实 JSON 中，出现“已通知”而 `submitted` 为空即拦截重写。
- 双轨影子比对：同一输入同时跑规则抽取与模型抽取，字段不一致的样本落表人工复核，形成回归集。
- 审计留痕：每条消息保存抽取 JSON 与事实 JSON，出问题可离线重放。
- 业务计数告警：每个事件的提醒数、每次审批的通知数与参会人数的比值偏离 1 即报警。
